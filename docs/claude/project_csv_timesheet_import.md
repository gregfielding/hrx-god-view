# csv timesheet import

> "Customer-CSV timesheet importer (new Timesheets tab): upload → parse/map → match worker by email → fill missing → review grid → submit to Everee. Architecture decisions + phase plan + Phase 0 state."

**Goal:** A new "Import CSV" tab in the Timesheets module where recruiters upload each customer's weekly timesheet CSV. Software parses (per-customer column mapping), matches each worker by **email** → HRX user → evereeWorkerId, best-effort pairs an HRX assignment, fills missing fields (pay rate, WC, worksite, position) — with **inline editing** in a review grid for gaps — then submits the batch to **Everee** (weekly timesheet / worked-shifts) for proper tax withholding + pay stubs.

**KEY ARCHITECTURE DECISION (worker-anchored, not assignment-anchored):** The existing timesheet system is assignment-anchored (`timesheet_entries` id = `{assignmentId}_{workDate}`; `createDraftTimesheetEntryCallable` requires an assignment + scheduled day). But Indeed-Flex/CORT workers are placed via Indeed and often have an HRX user + Everee linkage but **no HRX assignment**. The Everee submission contract is itself worker-anchored (needs `externalWorkerId`=HRX uid, start/end epoch, pay rate, WC code, work-location id, classified hours — NOT an assignment). → Build a **parallel worker-anchored import pipeline** (staging rows keyed on upload/row, externalId `{tenantId}::import::{uploadId}::{rowId}`) that reuses the Everee client + submit orchestration + grid cells, instead of forcing rows into the assignment-keyed model.

**Agreed decisions (2026-06-15):**
- Pay rate: from the **paired HRX assignment** first; gaps filled **inline** in the review grid (no per-customer default table). Hard gate: no submit without a confirmed pay rate.
- Unmatched workers (no HRX user / no Everee linkage / incomplete onboarding): **block + flag for onboarding**, never silently dropped. (Not auto-create.)
- Scope: **hardcode Indeed Flex first**, generalize the per-customer mapping framework later.

**Reuse map (Everee submit is the destination — all built):** `functions/src/payroll/createTimesheetBatch.ts` (entries must be status `approved`, ≤500/batch, creates `timesheet_batches`), `submitTimesheetBatch.ts` (orchestrator, pre-flight guards), `composeTimesheetBatchPayloads.ts` (externalId is assignment-keyed — needs a worker-anchored variant), `reconcileTimesheetBatches.ts` (15-min cron). Everee client: `functions/src/integrations/everee/` (evereeWorkedShifts, evereePayables, evereeHttp, evereeConfig). Worker-id resolve: `workerContextResolver.ts` → `users.evereeWorkerIds[evereeTenantId]` or `everee_workers`. Grid + cells: `src/components/timesheets/{TimesheetGrid,cells/*}`; resolution chains (WC + payRate) in `timesheetGridResolver.ts`. Email→user: `users.where('email','==',lc)` (mirror `findTenantUserByPhone` in jobOrderSheetSync.ts). Per-customer mapping pattern: mirror `venue_aliases` → `tenants/{t}/timesheet_column_mappings/{customerId}`. CSV parse: PapaParse (`src/utils/csvUpload.ts`). LLM column auto-detect: gpt-5 via the indeedFlex parser pattern. See [[feature_ts1_phase4_state]] (the Everee timesheet sync this builds on) + [[project_ai_provider_openai]].

**Indeed Flex CSV data gotchas:** `Hours` = NET payable hours (already minus break) — use directly. `Charge Rate` (24.84) = client **BILL** rate, NOT pay. `Timesheet Status`: import Approved/Submitted; skip Upcoming/Awaiting submission. `Didn't work` reason + Hours 0 = absence (skip). Email is the match key. `Site` string needs site→HRX worksite→Everee location mapping. Times are site-local → need worksite TZ for Everee epoch.

**Design framing for P3 (agreed in discussion):** The Everee-bound set per row is lean — `everee worker id · work date · hours · pay rate · WC class code · work-location`. Key distinctions: (1) **everee worker id is WORKER-side** (email→user→evereeWorkerIds), NOT from the JO. (2) **pay rate / WC code / position / worksite are JO-side, best reached via the ASSIGNMENT** (it links worker↔JO↔shift↔position for that date AND carries the snapshotted pay rate; grain = shift/position, since a multi-position JO varies). (3) **WC *rate* and *position/title* are NOT sent to Everee** — Everee's worked-shift call takes only the WC class *code*; the rate is internal cost/margin, position is just a resolution input. (4) The "Needs rate" rows = matched+linked workers with NO HRX assignment (typical for Indeed-placed crews) → no JO thread → P3 must connect them another way. **P3 DECISION (agreed 2026-06-15):** connect no-assignment rows to a JO+position via **Site→worksite→JO auto-mapping FIRST** (mirror venue_aliases — remember the mapping per Site string), with a **manual JO/position picker as the fallback** when auto-map can't resolve. Then the grid pivots from CSV-source columns to the editable Everee-bound set (Worker·Date·Hours·Pay rate·WC code·Worksite·Gross).
