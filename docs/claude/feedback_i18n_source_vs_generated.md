# i18n source vs generated

> Worker/jobs-board i18n keys must be edited in i18n/locales/*.json (source); public/i18n/locales/*.json are generated by the prebuild copy and get overwritten on every build

The worker-portal + jobs-board UI i18n (the `useT()` / `t('assignments.…')` system in `src/i18n/index.ts`) loads `public/i18n/locales/{en,es}.json` at runtime — but **those files are GENERATED, not source**. `package.json` `prebuild` runs `i18n:copy`, which `copyFileSync`s `i18n/locales/{en,es}.json` (repo root) → `public/i18n/locales/`. So every `npm run build` overwrites the public copies from the root source.

**Always add/edit keys in `i18n/locales/{en,es}.json` (the root source).** Editing only `public/i18n/locales/*.json` looks correct locally and even commits cleanly, but the next build silently wipes the change and the deploy ships raw key strings (e.g. a worker sees the literal `assignments.openShiftExplainer`). After editing the source, run `npm run i18n:copy` to regenerate public/ (or just let the build do it). Both layers are git-tracked. Fallback chain at runtime is es → en → key.

**Why:** caught this when slice-3 open-shift i18n keys were added only to public/ and the slice-3 build wiped them (commit `cbfefcd6` fixed it by adding to source). Same shape as the [[feedback_shared_mirror]] byte-mirror footgun — a generated copy that looks editable but isn't the source of truth.

**How to apply:** for any worker/jobs-board string, edit `i18n/locales/en.json` + `i18n/locales/es.json` (both languages), keep keys in the right namespace (e.g. `assignments`), then build. There's also `npm run i18n:check` (`scripts/i18n/check-i18n.ts`) to validate parity.
