# firebase spa route cache footgun

> "Firebase hosting header rules match REQUEST paths, not served files — SPA routes served via rewrite cached stale bundles for 1h after every deploy"

Firebase Hosting `headers` rules match the **request path**, not the file the rewrite serves. hrxone.com's `/index.html` rule had no-cache, but every real SPA route (`/crm`, `/jobs/...`) rewrites to index.html while inheriting the DEFAULT `max-age=3600` — so after each hosting deploy, users (and my own browser verification!) kept the old bundle up to an hour.

**Why:** cost a 3-deploy ghost chase on 2026-08-01 (Texas CRM tab "not updating" — the code was fine; the browser had a cached index.html). Verified with `performance.getEntriesByType('resource')` → old `main.<hash>.js` while the server already served the new hash.

**How to apply:** FIXED in firebase.json (commit 4c9f731c): catch-all `source: "**"` → `no-cache, must-revalidate` listed FIRST, then `/static/**` → `public, max-age=31536000, immutable` (CRA content-hashed assets) overriding after. When verifying a fresh deploy in a browser, add a throwaway query param (`?cachebust=...`) or confirm the served `main.*.js` hash matches `build/index.html` before debugging the code. Also remember: `curl -sI https://hrxone.com/<route> | grep -i cache-control` is the 5-second check.
