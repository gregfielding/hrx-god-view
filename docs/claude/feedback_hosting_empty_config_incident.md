# hosting deploy shipped an empty config — prod deep links 404'd (2026-08-25)

> "Firebase hosting deploys publish firebase.json's hosting block WITH the
> files — a deploy from the wrong directory erased every rewrite and served
> the raw CLI 404 on all deep links for ~2 hours."

**What happened:** Two hosting releases (8:19 PM and 8:32 PM PT, from Mark's
machine) carried `"config": {}` — no rewrites, no headers. The SPA catch-all
(`**` → `/index.html`) vanished, so every hard refresh and deep link on
hrxone.com returned Firebase's default 404 page (the "generated by the
Firebase Command-Line Interface" one). SPA navigation kept working (client
routing never asks the server), which made it look intermittent. Danny
reported it from the Placements tab at 10:41 PM; the release history API
(`firebasehosting.googleapis.com/v1beta1/sites/hrx1-d3beb/releases`) showed
the empty config and the deploying account. Fixed by redeploying from an
up-to-date repo-root checkout; all routes verified 200 with the correct
`no-cache` header.

**Why the config went empty:** the deploy was not run against the repo's
firebase.json. A stale checkout would still have carried the rewrites — an
EMPTY config means a different firebase.json entirely (classic causes:
running `firebase deploy` from another directory, or a `firebase init
hosting` that generated a bare config). The releases also overwrote that
day's shipped client features until the redeploy.

**Why (for both Claudes and both humans):** hosting deploys are
config+content atomic. There is no server-side protection against an empty
config — the CLI happily publishes it.

**How to apply — MANDATORY preflight for every `firebase deploy --only hosting`:**
1. Run ONLY from the hrx-god-view repo root. Never run `firebase init`.
2. `git pull` + `git log origin/main..main` empty (the stale-tree rule).
3. `grep -c '"destination": "/index.html"' firebase.json` → must be ≥ 1.
4. Build fresh, deploy, then verify:
   `curl -s -o /dev/null -w '%{http_code}' https://hrxone.com/jobs/job-orders`
   → must be `200`. A 404 here means the config was lost — redeploy from a
   correct checkout immediately and tell the other operator.
5. Announce hosting deploys to each other (same as functions deploys) —
   this incident was live for ~2 hours because nobody knew a deploy
   happened.

**Recovery if it recurs:** any up-to-date checkout, `npm run build`,
`firebase deploy --only hosting --project hrx1-d3beb`, re-run the curl
check. The release history endpoint above shows who/when if provenance is
unclear.
