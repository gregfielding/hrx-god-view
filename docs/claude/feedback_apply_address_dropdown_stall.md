# apply address dropdown stall

> apply-wizard dropdown-only address rule hard-stalled mobile signups (accounts w/o addresses); manual-entry + placesGeocodeAddress callable is the fix; browser Maps key CANNOT geocode (REQUEST_DENIED)

"Users signing up without home addresses" (recurring, 2026-08) was NOT a save bug: the apply wizard's address step required a Google Places **dropdown pick** (free-typed text deliberately cleared coords → `isApplyHomeAddressValid` fails → Next disabled). On phones where the dropdown doesn't engage, workers created accounts at step 0 (Personal Info) then stalled forever at step 1 and abandoned — `in_progress` applications with empty formData (interview scores still appear because the SMS prescreen is a separate flow). Fixed 024fb1cd: AddressStep manual-entry mode ("Can't find your address…? Enter it manually") geocodes via the `placesGeocodeAddress` callable and produces the same verified shape (normalized fields + coords + placeId), gate unchanged.

**Why:** the strict gate protected data quality but had no escape hatch; every "missing address" report pattern-matched to persistence when it was UX-blocked entry. Separate cohort: AuthDialog jobs-board signups (invite flows) create full user docs with EMPTY address and NO application — by design; address comes later via apply or onboarding.

**How to apply:** the browser Maps key is API-restricted — client-side geocoding (JS Geocoder AND the REST fetch in `src/utils/geocodeAddress.ts`) returns REQUEST_DENIED; any client geocode fallback MUST go through `placesGeocodeAddress` (server key, requires auth). Wizard's `ensurePersonalCoordinates` was silently dead for this reason until routed callable-first (024fb1cd). Related: [[feedback_apply_wizard_auth_step_drop]], [[feedback_addressinfo_dual_schema]].
